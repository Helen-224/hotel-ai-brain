## 4. 已完成的核心业务能力

### 4.1 统一模拟业务模型

src/data/hotelDemo.ts 集中维护房间、预订、服务需求、维修工单、业务任务、员工、班次、早餐服务、经营目标及运营事件。数据包含记录 ID 和关联关系，不只是手写指标卡。

模拟酒店有 100 间房；预订由 86 条在住和 25 条未来到店记录构成，按入住/离店时间计算当前与预测入住数量。包含 18 间待准备房、6 项维修、8 条 VIP 到店预订。早餐需求按相关预订与时段计算，岗位覆盖检查技能、班次和休息。以上都是固定场景数据，不是当前真实酒店经营信息。

### 4.2 三个运营事件

高峰入住准备连接维修、清洁、检查与交付依赖；早餐服务核对按时间段展示岗位覆盖缺口；VIP 接待关联到店、房间及服务需求。事件为预设记录，不具备自动发现任意新异常的能力。

### 4.3 四部门分析

src/data/agentAnalysis.ts 实现客房、工程、前厅、人力四个分析角色。输出事实、风险、理由、潜在影响、证据 ID、未知项、跨部门依赖和综合结论。分析读取当前内存状态，不创建业务任务。JSON 状态指纹用于标记旧分析过期。

这里的 Agent 是本地确定性规则函数，不是大模型调用，也没有独立 Agent 服务、工具调用网络或自主推理执行链。

### 4.4 资源方案

src/data/resourceCoordination.ts 和 src/ResourceCoordination.tsx 实现候选生成、基准比较、推荐、批准、退回、审批意见与历史记录。比较维度包含岗位缺口、任务调整、支援分钟、人员负荷和计划结束时间。

校验覆盖员工技能、班次、休息、跨部门支援窗口、任务时长、截止时间、前置依赖、维修预约、清洁与退房关系、人员时间冲突、每日容量及过期状态。它是有限模拟候选与规则校验，不是通用优化求解器。

批准资源方案只记录选择，不应用真实排班、不修改业务任务、不推进事件。事件审批和资源审批保持独立；同事件同业务版本的互斥方案只能批准一个。

### 4.5 执行追踪

事件可模拟通过、退回、重新提交；通过后关联已有业务任务，避免重复生成底层作业。任务可从待执行推进至进行中、执行完成；前置任务未满足时不能推进。共享任务状态通过事件转换同步，维修计数从任务状态派生。执行动作留在内存时间线。

执行完成、结果验证、事件解决是不同状态。现有转换函数没有完成通用业务验收或事件关闭的操作。因此可演示“执行完成但仍待验证”，不能演示完整的真实结果闭环。

## 8. 发现的问题与风险

1. 文档明显滞后：README 开头仍称第一轮介绍网站，后文却记录 3B-3；docs/README 仍称没有阶段验收记录，与 README 后续记录不一致。
2. 首页路线图滞后：Agent 与资源模拟仍标为规划，但平台已有本地规则分析和资源比较。应准确写为“规则模拟已实现，真实 AI 未接入”。
3. 版本口径不统一：Git 提交与 PRD 标识 0.4.1，package.json 仍为 0.1.0。
4. 导航入口与完成度不一致：五个管理入口为占位，演示时需避免把导航数量当成已完成模块数。
5. 刷新或离开平台重新进入会丢失模拟进度；URL 可恢复视图，不等于恢复审批和任务状态。
6. 资源审批没有应用阶段，执行链没有验证/关闭阶段，产品完整闭环仍缺后半段。
7. 规则风险与概览风险不是同一个指标：概览使用原事件等级，Agent 使用当前规则判断。源码有解释，但需继续保持文案清晰。
8. 状态指纹是整个 events 的 JSON，某事件变化可能令其他事件分析或方案失效；当前保守策略可用，扩展后可考虑更细的数据版本。
9. 部分页面和业务逻辑压缩在很长的代码行中，阅读、审查和局部修改成本偏高。
10. 真实安全治理未实现：前端角色选择仅是演示，不构成权限隔离；当前没有服务端密钥接入，不应把示例环境变量当成已配置能力。
